## 1. Цель работы

Научиться снимать трассу системных вызовов чужой программы с помощью `strace` и по ней понимать, что программа делает: какие вызовы она использует и для чего.

## 2. Что исследуется

- **Программа:** `bash` 5.2, командная оболочка Linux. В списке из задания есть `cmd` (оболочка Windows), `bash` это её аналог в Linux. Выбран потому, что оболочка как раз занимается тем, что проходят в курсе: запускает процессы, перенаправляет ввод-вывод, соединяет программы трубами.
- **ОС:** Ubuntu 24.04 в Docker на Mac (ядро Linux, архитектура aarch64).
- **Инструмент:** `strace` 6.8.

## 3. Как снималась трасса

Одна команда, в которой есть перенаправление в файл, конвейер и запуск внешней программы:

```sh
strace -f -y -o bash.log bash -c 'echo hello > out.txt; cat out.txt | wc -l; rm out.txt'
```

| Флаг | Что делает |
|---|---|
| `-f` | следить и за дочерними процессами (без него не видно, что делают `cat` и `wc`) |
| `-y` | рядом с номером дескриптора писать, что за ним стоит: `3</work/lab1/out.txt>`, `4<pipe:[79851]>` |
| `-o bash.log` | писать трассу в файл, а не в терминал |
| `-c` | вместо трассы вывести таблицу: сколько раз вызывался каждый вызов |

Результат: [bash.log](bash.log), 493 строки, 355 системных вызовов. В трассе три процесса:

| PID | Кто это |
|---|---|
| 149 | `bash`, в конце этот же процесс становится `rm` |
| 150 | `cat out.txt` |
| 151 | `wc -l` |

Сводка с флагом `-c` ([summary.txt](summary.txt)) снята той же командой (`strace -f -c bash -c '...' 2> summary.txt`), но позже и на другой машине: облачный Linux x86-64. Поэтому числа там немного другие (375 вызовов), и вместо `dup3`/`faccessat` там `dup2`/`access` (см. раздел 6). Таблица ниже посчитана по моему `bash.log`.

## 5. Разбор трёх фрагментов

Первые ~100 строк каждого процесса после `execve` это загрузка библиотек: `/etc/ld.so.cache`, `libc.so.6`, много `mmap`/`mprotect`/`close`. Это делает загрузчик `ld.so`, к командам оно отношения не имеет, при чтении я его пропускаю. Ошибки `ENOENT` при поиске программы по `PATH` (`/usr/local/sbin/cat`, `/usr/local/bin/cat`, ...) тоже норма: bash по очереди проверяет каталоги, пока не найдёт файл. Пути ниже немного сокращены.

### а) `echo hello > out.txt`

```
149 openat(AT_FDCWD, "out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3</.../out.txt>   открыли файл, получили номер 3
149 fcntl(1</dev/pts/0>, F_DUPFD, 10) = 10</dev/pts/0>                              копия старого stdout под номером 10
149 dup3(3</.../out.txt>, 1</dev/pts/0>, 0) = 1</.../out.txt>                       теперь 1 указывает на файл
149 close(3</.../out.txt>) = 0
149 write(1</.../out.txt>, "hello\n", 6) = 6                                        echo пишет в 1, а попадает в файл
149 dup3(10</dev/pts/0>, 1</.../out.txt>, 0) = 1</dev/pts/0>                         вернули stdout на терминал
149 close(10</dev/pts/0>) = 0
```

`echo` встроена в bash, нового процесса нет, поэтому bash перенаправляет свой собственный stdout, а потом возвращает его обратно из копии под номером 10. Номер 3 потому, что 0, 1, 2 заняты, а ядро выдаёт наименьший свободный.

### б) `cat out.txt | wc -l`

```
149 pipe2([3<pipe:[79851]>, 4<pipe:[79851]>], 0) = 0      труба: 3 для чтения, 4 для записи
149 clone(...SIGCHLD...) = 150                            процесс для cat
149 clone(...SIGCHLD...) = 151                            процесс для wc
149 close(4) ... close(3)                                 bash закрывает у себя оба конца
150 dup3(4<pipe>, 1</dev/pts/0>, 0) = 1<pipe>             cat: stdout -> труба
151 dup3(3<pipe>, 0</dev/pts/0>, 0) = 0<pipe>             wc: stdin <- труба
150 execve("/usr/bin/cat", ["cat", "out.txt"], ...) = 0
151 execve("/usr/bin/wc", ["wc", "-l"], ...) = 0
150 read(3</work/lab1/out.txt>, "hello\n", 131072) = 6
150 write(1<pipe>, "hello\n", 6) = 6                      cat пишет в трубу
151 read(0<pipe>, "hello\n", 16384) = 6                   wc читает из трубы
150 close(1<pipe>) = 0                                    cat закрыл запись...
151 read(0<pipe>, "", 16384) = 0                          ...и wc получил конец данных (EOF)
151 write(1</dev/pts/0>, "1\n", 2) = 2                    wc печатает результат
149 wait4(-1, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 150
149 wait4(-1, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 151
```

Схема: труба создаётся до `clone`, чтобы оба ребёнка унаследовали её концы; между `clone` и `execve` каждый ребёнок переклеивает свой конец на 0 или 1; после `execve` номера остаются. `wc` получил EOF только когда закрыты все концы записи: bash закрыл свой сразу, `cat` при выходе. Затем bash ждёт обоих детей через `wait4`. Ту же схему я использую в ЛР2.

### в) `rm out.txt`

```
149 newfstatat(AT_FDCWD, "/usr/local/sbin/rm", ...) = -1 ENOENT   поиск по PATH
149 newfstatat(AT_FDCWD, "/usr/local/bin/rm", ...)  = -1 ENOENT
149 newfstatat(AT_FDCWD, "/usr/sbin/rm", ...)       = -1 ENOENT
149 newfstatat(AT_FDCWD, "/usr/bin/rm", {st_mode=S_IFREG|0755, ...}) = 0   нашли
149 execve("/usr/bin/rm", ["rm", "out.txt"], ...) = 0             без clone!
149 unlinkat(AT_FDCWD, "out.txt", 0) = 0                          удаление файла
149 exit_group(0) = ?
```

`clone` здесь нет: `rm` последняя команда в `bash -c`, после неё bash делать нечего, и он сразу заменяет себя на `rm` через `execve`. Поэтому `rm` работает под тем же PID 149.

## 6. Почему в трассе не те имена, что в C-коде

`strace` показывает вызовы ядра, а в C мы вызываем функции glibc. glibc часто реализует старую функцию через более новый вызов:

| В коде на C | В трассе | Почему |
|---|---|---|
| `fork()` | `clone(...SIGCHLD...)` | `clone` общий вызов создания процесса/потока, `fork` это его частный случай |
| `open()` | `openat(AT_FDCWD, ...)` | `AT_FDCWD` значит "путь от текущего каталога", то же самое, что `open` |
| `pipe()` | `pipe2(..., 0)` | `pipe2` это `pipe` с флагами, флаги 0 |
| `waitpid()` | `wait4()` | `wait4` это `waitpid` с дополнительной статистикой |
| `dup2()` | `dup3()` на aarch64, `dup2()` на x86-64 | в ядре для aarch64 нет старого `dup2`, только `dup3`. В облачной сводке x86-64 ([summary.txt](summary.txt)) видно `dup2` |

Аналогично на aarch64 нет `access` и `stat`, поэтому `faccessat` и `newfstatat`; на x86-64 в сводке встречается `access`.

## 8. Выводы

1. Трасса `bash` для одной строки из трёх команд содержит 355 системных вызовов в трёх процессах. Больше всего вызовов про файлы (130) и память (74), но в основном это загрузка библиотек, а не сами команды.
2. Работа оболочки сводится к нескольким вызовам: `clone` создаёт процесс, `dup3` переклеивает дескрипторы для `>` и `|`, `execve` запускает программу, `wait4` ждёт её завершения. Труба создаётся через `pipe2` до `clone`.
3. Встроенная команда (`echo`) с перенаправлением работает без нового процесса: bash сохраняет и восстанавливает свой stdout. Последнюю команду bash запускает через `execve` без `clone`.
4. Ошибки `ENOENT` в трассе не сбои: так выглядит поиск программы по `PATH` и попытка подключиться к отсутствующему nscd.
5. Имена вызовов в трассе отличаются от функций C (`clone` вместо `fork` и т. д.), потому что glibc реализует их через более общие вызовы ядра, а набор вызовов зависит от архитектуры.
