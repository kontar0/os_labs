## 1. Цель работы

Приобретение практических навыков диагностики работы программного обеспечения: снятие трассы системных вызовов стороннего ПО, составление его профиля и сопоставление системных вызовов с функционалом программы.

## 2. Задание

Выбрать стороннее ПО и составить профиль его системных вызовов средствами диагностики ОС. Профиль должен содержать группы найденных системных вызовов и указание, для какого функционала ПО они вызывались. Работа сквозная: для каждой следующей ЛР строится профиль собственной программы (раздел 7).

- **ОС:** Linux (Ubuntu 24.04 LTS, ядро Linux, архитектура aarch64)
- **Исследуемое ПО:** командный интерпретатор `bash` 5.2 — Linux-аналог `cmd`/`PowerShell` из списка ТЗ
- **Средство диагностики:** `strace` 6.8

## 3. Методика

Чтобы профиль был воспроизводимым, `bash` выполняет фиксированный сценарий [scenario.sh](scenario.sh), который задействует основные функции оболочки:

| № | Команда сценария | Проверяемый функционал bash |
|---|---|---|
| 1 | `cd /tmp` | смена рабочего каталога |
| 2 | `echo "hello from $NAME" > out.txt` | переменные, встроенная команда, перенаправление вывода в файл |
| 3 | `echo "second line" >> out.txt` | дозапись в файл |
| 4 | `cat out.txt \| wc -l` | конвейер: канал + два дочерних процесса |
| 5 | `while read -r line; do :; done < out.txt` | перенаправление ввода, встроенная `read` |
| 6 | `ls -l out.txt > /dev/null` | поиск программы в `PATH`, запуск внешней программы |
| 7 | `( sleep 0.1 )` | подоболочка, ожидание завершения |
| 8 | `rm out.txt` | удаление файла внешней утилитой |

Профиль снимает скрипт [profile.sh](profile.sh):

```sh
strace -f -tt -s 64 -o traces/bash.log     bash scenario.sh   # полная трасса с временем
strace -f -c        -o traces/bash.summary bash scenario.sh   # статистика по вызовам
```

- `-f` — трассировать и дочерние процессы (bash сам создаёт процессы для `cat`, `wc`, `ls`...);
- `-tt` — метка времени с микросекундами, чтобы видеть порядок событий;
- `-c` — сводная таблица: количество вызовов, ошибок, время.

Затем `profile.sh` раскладывает вызовы по группам (файл `traces/bash.groups`).
Запуск всего: `./linux.sh sh -c 'cd lab1 && ./profile.sh bash bash /work/lab1/scenario.sh'`.

> Платформа aarch64: здесь у ядра нет отдельных вызовов `open`, `dup2`, `fork`, `pipe`, `stat`. Библиотека glibc реализует их через `openat`, `dup3`, `clone`, `pipe2`, `newfstatat`. На x86-64 в трассе были бы `dup2`/`pipe` и т. д., но по смыслу это те же операции.

## 5. Профиль системных вызовов bash (по группам)

| Группа | Системные вызовы (кол-во) | Для какого функционала bash они вызывались |
|---|---|---|
| **1. Управление процессами** (64) | `clone`(5), `execve`(6), `wait4`(9), `exit_group`, `getpid`(8), `getppid`(3), `getpgid`, `set_tid_address`, `set_robust_list`, `rseq`, `prlimit64`, `uname` | `clone` — создание дочернего процесса (это `fork()` в glibc) для каждой внешней команды и подоболочки; `execve` — замена образа процесса на `/usr/bin/cat`, `wc`, `ls`, `sleep`, `rm`; `wait4` — ожидание завершения детей и получение кода возврата (`$?`). Вызов `wait4(-1, …, WNOHANG)` в обработчике SIGCHLD собирает завершившихся детей, чтобы не было зомби. `getpgid`/`getpid` — управление заданиями (job control). `set_tid_address`, `set_robust_list`, `rseq`, `prlimit64` — инициализация потока при старте каждой программы в glibc |
| **2. Файлы и дескрипторы** (296) | `openat`(29), `read`(31), `write`(5), `close`(60), `newfstatat`(55), `fstat`(29), `faccessat`(19), `lseek`(14), `fcntl`(19), `dup3`(10), `ioctl`(16), `chdir`, `unlinkat`, `statx`, `listxattr` | `openat` — загрузка динамических библиотек, открытие `out.txt` для `>` (`O_WRONLY\|O_CREAT\|O_TRUNC`), `>>` (`O_APPEND`) и `<` (`O_RDONLY`); `read` — чтение скрипта по частям (`read(255, …)`) и данных файла; `newfstatat`/`faccessat` — поиск исполняемого файла в каталогах `PATH` (ошибки `ENOENT` означают, что в этом каталоге программы нет); `fcntl(1, F_DUPFD, 10)` + `dup3` — сохранение и восстановление stdout при перенаправлении; `lseek` — возврат на позицию в файле скрипта; `ioctl(TCGETS/TIOCGPGRP)` — проверка, подключён ли терминал (ошибки `ENOTTY`, т. к. запуск не интерактивный); `chdir` — `cd /tmp`; `unlinkat` — удаление файла в `rm`; `statx`, `listxattr` — получение атрибутов файла в `ls -l` |
| **3. Межпроцессное взаимодействие** (13) | `pipe2`(1), `socket`(6), `connect`(6, все с ошибкой) | `pipe2` — неименованный канал для конвейера `cat \| wc`. `socket`/`connect` к `AF_UNIX`-сокету — попытка обратиться к демону `nscd`/`systemd-userdb` за именами пользователей (bash и `ls -l` переводят UID→имя). В контейнере такого демона нет, поэтому `ENOENT` и переход на чтение `/etc/passwd` |
| **4. Сигналы** (115) | `rt_sigaction`(57), `rt_sigprocmask`(54), `rt_sigreturn`(4) | `rt_sigaction` — установка обработчиков SIGCHLD, SIGINT и др.; в дочернем процессе перед `execve` обработчики сбрасываются в `SIG_DFL`. `rt_sigprocmask(SIG_BLOCK, [CHLD])` — блокировка SIGCHLD на время `fork`, чтобы не было гонки между созданием ребёнка и его учётом в таблице заданий. `rt_sigreturn` — возврат из обработчика SIGCHLD |
| **5. Управление памятью** (121) | `mmap`(49), `mprotect`(30), `munmap`(24), `brk`(18) | `mmap` — отображение в память динамических библиотек (`libc.so.6`, `libtinfo.so.6` и др.) и анонимные выделения; `mprotect` — выставление прав доступа для сегментов загруженных библиотек (RELRO); `brk` — увеличение кучи для `malloc` (переменные, разбор команд) |
| **6. Окружение, время** (59) | `getuid`/`geteuid`/`getgid`/`getegid`(по 13), `getrandom`(6), `clock_nanosleep`(1) | Идентификаторы пользователя — для переменных `$UID`/`$EUID` и проверки прав; `getrandom` — инициализация `$RANDOM` и защиты кучи в glibc; `clock_nanosleep` — сама пауза в `sleep 0.1` |

## 6. Разбор ключевых фрагментов трассы

### 6.1. Перенаправление вывода `echo … > out.txt` (встроенная команда, без нового процесса)

```
13 openat(AT_FDCWD, "out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3   # открыли файл
13 fcntl(1, F_DUPFD, 10)          = 10   # сохранили старый stdout в fd 10
13 fcntl(10, F_SETFD, FD_CLOEXEC) = 0    # чтобы копия не «утекла» в дочерние процессы
13 dup3(3, 1, 0)                  = 1    # stdout теперь указывает на out.txt
13 close(3)                       = 0
13 write(1, "hello from oslab\n", 17) = 17
13 dup3(10, 1, 0)                 = 1    # вернули прежний stdout
13 close(10)                      = 0
```

`echo` — встроенная команда, поэтому bash перенаправляет **свой** stdout и потом восстанавливает его.

### 6.2. Конвейер `cat out.txt | wc -l`

```
13 pipe2([3, 4], 0)                          = 0      # канал: 3 — чтение, 4 — запись
13 clone(...SIGCHLD...)                      = 14     # ребёнок для cat
13 clone(...SIGCHLD...)                      = 15     # ребёнок для wc
14 dup3(4, 1, 0)                             = 1      # cat: stdout -> канал
15 dup3(3, 0, 0)                             = 0      # wc:  stdin  <- канал
14 execve("/usr/bin/cat", ["cat", "out.txt"], ...) = 0
15 execve("/usr/bin/wc", ["wc", "-l"], ...)  = 0
13 wait4(-1, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 14
13 wait4(-1, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 15
```

Это та же схема `pipe → fork → dup2 → exec → wait`, которая используется в ЛР2.

### 6.3. Запуск внешней программы `ls` и поиск в PATH

```
13 newfstatat(AT_FDCWD, "/usr/local/sbin/ls", ...) = -1 ENOENT
13 newfstatat(AT_FDCWD, "/usr/local/bin/ls", ...)  = -1 ENOENT
...
13 newfstatat(AT_FDCWD, "/usr/bin/ls", {st_mode=S_IFREG|0755, ...}) = 0
13 clone(...)                                      = 16
16 dup3(3, 1, 0)                                   = 1      # > /dev/null
16 execve("/usr/bin/ls", ["ls", "-l", "out.txt"], ...) = 0
16 statx(AT_FDCWD, "out.txt", ...)                 = 0      # атрибуты для -l
```

Ошибки `ENOENT` здесь — нормальная работа, а не сбой: bash по очереди проверяет каталоги из `PATH`.

## 7. Сквозной профиль: программа ЛР2

Профиль программы ЛР2 (вариант 6) снят тем же скриптом:
`STDIN_FILE=… ./profile.sh lab2 /work/lab2/build/parent` → [traces/lab2.log](traces/lab2.log), [traces/lab2.summary](traces/lab2.summary).

| Группа | Вызовы | Где в коде ЛР2 и зачем |
|---|---|---|
| Процессы | `clone`(1), `execve`(2), `wait4`(1), `exit_group` | `fork()` в `spawn_redirected`, `execv(child)`, `waitpid` в `wait_child` — создание ребёнка и ожидание его завершения без зомби |
| Файлы/дескрипторы | `read`(9), `write`(11), `openat`, `close`(10), `dup3`(2), `readlinkat` | `read(0)` — имя файла от пользователя; `openat(file, O_RDONLY)` — файл команд; `dup3(file,0)` и `dup3(pipe[1],1)` — подмена stdin/stdout ребёнка; `close` неиспользуемых концов канала; `readlinkat("/proc/self/exe")` — поиск программы `child` |
| IPC | `pipe2`(1) | `pipe()` — создание pipe1 (ребёнок → родитель) |
| Сигналы | `rt_sigaction`(2) | Игнорирование SIGPIPE в обоих процессах, чтобы обрыв канала давал `EPIPE`, а не убивал процесс |
| Память | `mmap`, `brk`, ... | загрузка libc и буфер строки (`realloc`) |

Всего 99 вызовов (против ~670 у bash): программа делает только то, что нужно по заданию. Подробный разбор трассы — в отчёте ЛР2.

## 8. Выводы

1. С помощью `strace -f` построен профиль системных вызовов `bash`: ~670 вызовов в 6 процессах, разложенных на 6 функциональных групп.
2. Работа с файлами и дескрипторами — самая многочисленная группа (≈44 %): загрузка библиотек, поиск программ в `PATH`, перенаправления.
3. Основную функцию оболочки (запуск команд) обеспечивает связка `clone` → `dup3` → `execve` → `wait4`. Перенаправления и конвейеры сделаны через `openat`/`pipe2` + `dup3`, а у встроенных команд ещё и через сохранение дескриптора в `fcntl(F_DUPFD)`.
4. Ошибки в трассе (`ENOENT`, `ENOTTY`) — не сбои. Это нормальные проверки: поиск в `PATH` и проверка, подключён ли терминал.
5. Тот же механизм `pipe → fork → dup2 → exec → wait` реализован в ЛР2, и в её трассе он виден в чистом виде. Профили следующих лабораторных будут добавляться в раздел 7.
