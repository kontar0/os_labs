## 1. Программа и процесс

**Программа** это файл на диске, рецепт: `/usr/bin/cat`, `lab2/parent`. Сам по себе он ничего не делает.

**Процесс** это запущенная программа. У процесса есть:

- **PID**, номер процесса (в твоей трассе bash это 149, cat 150, wc 151);
- своя память (код, данные, стек, куча);
- **таблица дескрипторов**: какие файлы, терминалы, трубы у него открыты;
- родитель (PPID), код выхода, обработчики сигналов и т. д.

Одна программа может работать в нескольких процессах сразу (два терминала с bash это два процесса одной программы `/usr/bin/bash`). И наоборот, один процесс может сменить программу (через `exec`, раздел 6).

**Модель "комната с окошком".** Процесс сидит в закрытой комнате. Внутри он может считать что угодно: складывать числа, гонять циклы, это просто инструкции процессора. Но в комнате нет ни диска, ни экрана, ни клавиатуры, ни других процессов. Всё общение с миром идёт через одно окошко к ядру: "открой файл", "запиши эти байты в номер 1", "создай копию меня", "дай мне PID". Каждая такая просьба это **системный вызов**.

`strace` подслушивает у окошка: печатает каждую просьбу, её аргументы и ответ ядра. Что процесс делает внутри комнаты (удаление гласных в `remove_vowels`), strace не видит. Поэтому в трассе ЛР2 нет "удаления гласных", есть только `read` строк и `write` результатов.

## 2. Системный вызов на уровне регистров

В твоём загрузчике на NASM ты делал так:

```nasm
mov ah, 0x0E      ; функция BIOS: вывести символ
mov al, 'h'       ; какой символ
int 0x10          ; позвать BIOS
```

Системный вызов Linux выглядит так же: кладёшь номер "функции" и аргументы в регистры и выполняешь специальную инструкцию.

**Linux arm64 (твой Mac в Docker):** номер вызова в `x8`, аргументы в `x0`...`x5`, инструкция `svc #0`, результат возвращается в `x0`.

```asm
mov x0, #1          // аргумент 1: fd = 1 (stdout)
adr x1, msg         // аргумент 2: адрес строки
mov x2, #6          // аргумент 3: длина
mov x8, #64         // номер вызова write на arm64
svc #0              // в ядро; в x0 вернётся число записанных байт
```

**Linux x86-64:** номер в `rax`, аргументы в `rdi, rsi, rdx, r10, r8, r9`, инструкция `syscall`, результат в `rax`.

```nasm
mov rax, 1          ; номер write на x86-64
mov rdi, 1          ; fd
lea rsi, [rel msg]  ; адрес
mov rdx, 6          ; длина
syscall
```

**Старый 32-битный x86:** `int 0x80`, номер в `eax`, аргументы в `ebx, ecx, edx, esi, edi, ebp`. Это прямо как твой `int 0x10`, только позвали не BIOS, а ядро.

Номера вызовов на разных архитектурах разные (из заголовков `asm-generic/unistd.h` и `asm/unistd_64.h`):

| Вызов | arm64 | x86-64 |
|---|---|---|
| `read` | 63 | 0 |
| `write` | 64 | 1 |
| `openat` | 56 | 257 |
| `close` | 57 | 3 |
| `dup2` | нет | 33 |
| `dup3` | 24 | 292 |
| `pipe2` | 59 | 293 |
| `clone` | 220 | 56 |
| `execve` | 221 | 59 |
| `wait4` | 260 | 61 |
| `exit_group` | 94 | 231 |

**Чем отличается от `int 0x10`.** BIOS в реальном режиме это просто код, который выполняется с теми же правами, что и твой загрузчик: он может трогать любую память и любое железо. `svc`/`syscall` переключает процессор в привилегированный режим (EL1 на ARM, ring 0 на x86), и дальше работает ядро. Оно проверяет аргументы: твой ли это дескриптор, принадлежит ли адрес буфера твоему процессу, есть ли права на файл. Поэтому окошко одно, и через него нельзя "залезть" в чужую комнату.

**Ошибки.** Ядро возвращает отрицательное число, например `-2` (это `-ENOENT`). Обёртка из glibc превращает это в `-1` и кладёт `2` в переменную `errno`. `perror` печатает текст для текущего `errno`: `No such file or directory`. strace показывает это как `= -1 ENOENT (No such file or directory)`.

**Почему в C мы не пишем `svc` руками.** Функции `read`, `write`, `fork`, `pipe` из `<unistd.h>` это маленькие обёртки в glibc: разложить аргументы по регистрам, сделать `svc`/`syscall`, обработать ошибку. Иногда обёртка зовёт другой вызов, чем её имя (раздел 11.5).

## 3. Дескрипторы: номерки в гардеробе

**Дескриптор** это маленькое целое число, по которому процесс обращается к открытому файлу. Модель: гардероб. Ты отдаёшь вещь (файл), получаешь номерок (число). Дальше говоришь не "запиши в out.txt", а "запиши в номерок 3".

```
149 openat(AT_FDCWD, "out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3</.../out.txt>
149 write(1</.../out.txt>, "hello\n", 6) = 6
149 close(3</.../out.txt>) = 0
```

Правила:

- **0, 1, 2 это соглашение, а не магия ядра.** 0 = stdin (откуда читать), 1 = stdout (куда писать результат), 2 = stderr (куда писать ошибки). Ядру всё равно, это просто первые три номерка. Программы договорились, что `printf` пишет в 1, `scanf` читает из 0, `perror` пишет в 2. Обычно все три указывают на терминал (`/dev/pts/0` в твоей трассе).
- **Ядро выдаёт наименьший свободный номер.** 0, 1, 2 заняты, поэтому первый `open` вернул 3. Если закрыть 0 и потом сделать `open`, получишь 0.
- **За номерком может быть что угодно:** файл, терминал, труба, сокет, `/dev/null`. `read` и `write` работают одинаково со всеми. Поэтому `cat` не знает и не должен знать, пишет он в терминал или в трубу.
- **Номерки у каждого процесса свои.** 3 у bash и 3 у cat могут указывать на разные вещи.

Посмотреть номерки живого процесса: `ls -l /proc/<PID>/fd`. В strace их показывает флаг `-y`: `4<pipe:[79851]>` значит "номер 4, за ним труба с внутренним номером 79851".

## 4. dup2: переклеить номерок

`dup2(старый, новый)` делает так, чтобы номер `новый` указывал туда же, куда `старый`. Если `новый` был открыт, он сначала закрывается. После этого у вещи два номерка, и лишний обычно закрывают.

Перенаправление `echo hello > out.txt` из твоей трассы:

```
149 openat(AT_FDCWD, "out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3     out.txt под номером 3
149 fcntl(1</dev/pts/0>, F_DUPFD, 10) = 10</dev/pts/0>                  запасной номерок 10 на терминал
149 dup3(3</.../out.txt>, 1</dev/pts/0>, 0) = 1</.../out.txt>           переклеили: 1 теперь out.txt
149 close(3</.../out.txt>) = 0                                          3 больше не нужен
149 write(1</.../out.txt>, "hello\n", 6) = 6                            echo пишет "в stdout", а попадает в файл
149 dup3(10</dev/pts/0>, 1</.../out.txt>, 0) = 1</dev/pts/0>             вернули 1 на терминал
149 close(10</dev/pts/0>) = 0
```

`echo` встроена в bash, поэтому bash переклеивает **свой** stdout и потом возвращает его из запасного номера 10. Для внешней программы (cat, ls) bash переклеивает номерки уже в ребёнке, и возвращать ничего не надо (раздел 12).

`dup3` это `dup2` с третьим аргументом-флагами (тут 0). На arm64 в ядре нет `dup2`, только `dup3`, поэтому glibc зовёт его. На x86-64 в трассе будет `dup2`.

## 5. fork: копия комнаты

`fork()` создаёт новый процесс, почти точную копию текущего: та же программа, та же память (копия), **копия таблицы дескрипторов**, то же место в коде. Оба процесса продолжают с инструкции после `fork`. Различаются только возвращаемым значением:

| Кто | Что вернул `fork` |
|---|---|
| родитель | PID ребёнка (> 0) |
| ребёнок | 0 |
| ошибка (ребёнок не создан) | -1 |

```c
pid_t pid = fork();
if (pid == -1) { /* ошибка */ }
if (pid > 0)   { /* это родитель, pid = PID ребёнка */ }
/* сюда доходит только ребёнок */
```

Память копируется не сразу, а при первой записи (copy-on-write), так что `fork` дешёвый.

**Зачем копия, если потом всё равно `exec`?** Ради момента между `fork` и `exec`. В этот момент код ещё наш (родительский), но работает уже в новом процессе. Здесь мы переклеиваем номерки ребёнка (`dup2`), закрываем лишнее, и только потом запускаем чужую программу. Родитель при этом не трогается: его stdin/stdout остаются прежними. Если бы bash сделал `exec cat` сам в себе, bash бы исчез (так и происходит с последним `rm` в твоей трассе: там bash больше не нужен).

Номерки после `fork`: у ребёнка свои номерки, но вешалки те же. Если родитель открыл файл под номером 3, у ребёнка тоже есть 3, указывающий на тот же открытый файл (с той же позицией чтения). Закрытие 3 у ребёнка не закрывает 3 у родителя.

В трассе `fork` выглядит как `clone(child_stack=NULL, flags=...|SIGCHLD, ...) = 150`. `clone` это общий вызов ядра для создания процессов и потоков, glibc реализует `fork` через него. Строки с PID ребёнка начинаются сразу после `clone`.

## 6. exec: сменить программу, оставить номерки

`execve(путь, argv, env)` загружает в текущий процесс другую программу. Старый код, данные, стек выбрасываются. **PID остаётся тот же, таблица дескрипторов остаётся та же** (кроме помеченных `O_CLOEXEC`). Обработчики сигналов сбрасываются в "по умолчанию", но "игнорировать" сохраняется.

```
150 dup3(4<pipe:[79851]>, 1</dev/pts/0>, 0) = 1<pipe:[79851]>    ещё bash-код в процессе 150
150 execve("/usr/bin/cat", ["cat", "out.txt"], ...) = 0          теперь в 150 работает cat
150 write(1<pipe:[79851]>, "hello\n", 6) = 6                     cat пишет в 1, а там труба
```

- При успехе `exec` **не возвращается**: возвращаться некуда, старого кода больше нет. Если строка после `exec` выполнилась, значит он не удался. Поэтому в ЛР2 после `execl` сразу `perror` и `_exit(1)` без всякого `if`.
- `execl(path, arg0, arg1, ..., NULL)` и `execv(path, argv)` это обёртки над одним `execve`: первая принимает аргументы списком, вторая массивом.
- `execl`/`execv` **не ищут** программу по `PATH`, путь берётся как есть. `execlp`/`execvp` ищут. bash ищет сам: перебирает каталоги из `PATH` через `newfstatat`, отсюда `ENOENT` в трассе.
- После `execve` в трассе идут ~100 строк загрузки libc: это работает загрузчик `ld.so` внутри новой программы.

## 7. pipe: труба с двумя номерками

`pipe(fds)` создаёт в ядре буфер-трубу и даёт два номерка: `fds[0]` для чтения, `fds[1]` для записи. Что записали в `fds[1]`, можно прочитать из `fds[0]`, по порядку, байтами.

```
149 pipe2([3<pipe:[79851]>, 4<pipe:[79851]>], 0) = 0     3 чтение, 4 запись, одна и та же труба 79851
```

**Труба в одном процессе бесполезна**: писать самому себе можно и в память. Смысл появляется вместе с `fork`: ребёнок получает копии обоих номерков, и у двух процессов появляется общий канал.

**Почему `pipe` до `fork`.** Номерки наследуются только при `fork`. Если создать трубу после `fork`, у родителя и ребёнка будут две разные трубы, ничем не связанные. Труба безымянная, найти её потом по имени нельзя.

**Правила, которые надо знать:**

1. `read` из пустой трубы ждёт, пока кто-то запишет.
2. `write` в полную трубу ждёт, пока кто-то прочитает. Размер буфера в Linux обычно 64 КБ (проверено: `F_GETPIPE_SZ` = 65536).
3. **`read` возвращает 0 (EOF) только когда закрыты ВСЕ номерки записи** во всех процессах. Пока хоть один `fds[1]` где-то открыт, ядро считает, что данные ещё могут прийти, и `read` ждёт.
4. `write` в трубу, у которой закрыты все номерки чтения: ядро шлёт писателю сигнал `SIGPIPE` (по умолчанию убивает процесс). Если `SIGPIPE` игнорировать, `write` вернёт `-1` с `errno = EPIPE`.

Из правила 3 следует главное правило ЛР2: **каждый процесс закрывает концы, которыми не пользуется.** Родитель только пишет, поэтому сразу закрывает концы чтения `pipe1[0]` и `pipe2[0]`, а когда строки кончились, закрывает и концы записи. Каждый ребёнок оставляет себе только свою трубу (как stdin) и закрывает всё остальное, в том числе **чужой** конец записи. Если кто-то держит лишний конец записи, ребёнок никогда не получит EOF, и программа зависнет во взаимоблокировке (проверено, раздел 16.3).

В твоей трассе это видно: `wc` получил `read(...) = 0` сразу после того, как `cat` сделал `close(1<pipe>)` при выходе. bash свои концы закрыл ещё раньше.

## 8. Зомби и waitpid

Когда процесс завершается, ядро освобождает его память и закрывает его номерки, но оставляет маленькую запись: PID и код выхода. Ждёт, пока родитель её заберёт. Процесс в этом состоянии называется **зомби** (в `ps` состояние `Z`, `<defunct>`).

Забирает запись `waitpid(pid, &status, 0)`: ждёт, пока ребёнок завершится, кладёт в `status` как он завершился, и удаляет зомби. В трассе это `wait4`:

```
11 wait4(13, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 13
```

Разбор `status` макросами:

- `WIFEXITED(status)`: вышел сам (через `return` из `main` или `exit`), тогда `WEXITSTATUS(status)` это код выхода;
- `WIFSIGNALED(status)`: убит сигналом, тогда `WTERMSIG(status)` это номер сигнала.

Если родитель не вызывает `waitpid`, ребёнок висит зомби, пока жив родитель. Когда родитель умирает, его детей (и живых, и зомби) "усыновляет" процесс с PID 1 (init), и он их убирает. Поэтому зомби это проблема долгоживущих программ (серверов), но в лабораторной требуют `waitpid` всегда.

Когда ребёнок завершается, родитель получает сигнал `SIGCHLD`. В трассе ЛР2: `--- SIGCHLD {si_pid=13, si_status=0, ...} ---`. По умолчанию он ничего не делает. bash ставит на него обработчик и в нём вызывает `wait4(-1, ..., WNOHANG)` (строка 432 в `bash.log`).

## 9. Сигналы

Сигнал это уведомление процессу от ядра (или от другого процесса через `kill`). Аналогия с твоим загрузчиком: прерывание. Процесс что-то делает, и вдруг ядро прерывает его и говорит "случилось X".

У каждого сигнала есть действие: по умолчанию (`SIG_DFL`, обычно убить процесс), игнорировать (`SIG_IGN`) или свой обработчик (функция).

| Сигнал | Номер | Откуда | По умолчанию | Можно перехватить |
|---|---|---|---|---|
| `SIGINT` | 2 | Ctrl+C в терминале | завершить | да |
| `SIGQUIT` | 3 | Ctrl+\ | завершить + core dump | да |
| `SIGKILL` | 9 | `kill -9 PID` | завершить | **нет** |
| `SIGSEGV` | 11 | обращение к чужой памяти | завершить + core | да |
| `SIGPIPE` | 13 | `write` в трубу без читателей | завершить | да |
| `SIGTERM` | 15 | `kill PID` (по умолчанию) | завершить | да |
| `SIGCHLD` | 17 | ребёнок завершился | ничего | да |
| `SIGSTOP` | 19 | `kill -STOP` | остановить | **нет** |

- `SIGTERM` это вежливая просьба завершиться: программа может поймать его, сохранить данные и выйти. `SIGKILL` ядро выполняет само, процесс даже не узнает. Его нельзя ни перехватить, ни игнорировать, иначе нельзя было бы убить зависшую программу.
- Если процесс убит сигналом N, shell показывает код выхода `128 + N`. Ctrl+C даёт `130`, `kill -9` даёт `137`.
- **Ctrl+C.** В загрузчике ты получал Ctrl+C как байт `0x03` через `int 0x16`: ОС не было, байт приходил тебе как есть. В Linux между клавиатурой и программой стоит драйвер терминала. Он видит байт `0x03`, не передаёт его программе, а отправляет `SIGINT` всем процессам переднего плана этого терминала (группе процессов). В ЛР2 это и `parent`, и `child`: ребёнок после `fork` в той же группе. Оба умрут.
- **`SIG_IGN` переживает `exec`.** Проверено: `sh -c 'trap "" PIPE; exec grep SigIgn /proc/self/status'` показывает `SigIgn: 0000000000001000`, это бит 13, `SIGPIPE`. Обработчик-функция `exec` не переживает: её кода больше нет в памяти. Поэтому bash в ребёнке перед `execve` сбрасывает свои обработчики в `SIG_DFL` (в трассе `rt_sigaction(SIGINT, {sa_handler=SIG_DFL, ...})`).
- `rt_sigaction` в трассе это `signal`/`sigaction` из C. `rt_sigprocmask` это временная блокировка сигналов: bash блокирует `SIGCHLD` на время `clone`, чтобы обработчик не сработал, пока ребёнок не записан в таблицу заданий.

В ЛР2 оба процесса делают `signal(SIGPIPE, SIG_IGN)`. Тогда обрыв трубы превращается из внезапной смерти в обычную ошибку `write` с `EPIPE`, которую мы печатаем и аккуратно завершаемся.

## 10. Терминал и канонический режим

Когда ты набираешь в терминале строку, программа получает её не по буквам, а целиком после Enter. Это делает драйвер терминала в ядре, режим называется **канонический**. Посмотреть настройки: `stty -a`.

```
intr = ^C; quit = ^\; erase = ^?; kill = ^U; eof = ^D; susp = ^Z; ...
isig icanon echo ...
```

| Клавиша | Настройка | Что делает драйвер |
|---|---|---|
| Ctrl+C | `intr` | шлёт `SIGINT` группе переднего плана |
| Ctrl+\ | `quit` | шлёт `SIGQUIT` |
| Ctrl+Z | `susp` | шлёт `SIGTSTP` (приостановить) |
| Backspace | `erase` | стирает символ в ещё не отправленной строке |
| Ctrl+U | `kill` | стирает всю строку (не путать с сигналом) |
| Ctrl+D | `eof` | отдаёт строку без Enter; в начале строки `read` вернёт 0 = конец ввода |

Флаги: `icanon` канонический режим (копить строку), `isig` превращать ^C, ^\, ^Z в сигналы, `echo` показывать набранное. В твоей трассе это видно: `rm` спросил у терминала настройки:

```
149 ioctl(0</dev/pts/0>, TCGETS, {..., c_lflag=ISIG|ICANON|ECHO|ECHOE|ECHOK|IEXTEN|ECHOCTL|ECHOKE, ...}) = 0
```

`stty raw -echo` выключает всё это: программа получает каждый байт сразу, Ctrl+C приходит как `0x03`. Это ровно то, что было в твоём загрузчике (так работают vim, top, игры в терминале). Вернуть: `stty sane`.

Для ЛР2: если запустить `./parent` без `echo ... |`, драйвер отдаст родителю имя файла только после Enter, а Ctrl+D на пустой строке даст `fgets` конец ввода и сообщение "имя файла не введено".

## 11. Как читать strace

### 11.1. Структура одной строки

```
150   write(1<pipe:[79851]>, "hello\n", 6) = 6
│     │     │                            │
кто   что   с чем                        результат
```

Читай как фразу: "процесс 150 попросил записать в номер 1 (это труба) 6 байт `hello\n`, ядро записало 6". Результат `-1 ENOENT (...)` значит ошибку и её причину.

### 11.2. Структура жизни процесса

Любой процесс в трассе выглядит так:

1. `execve(...)` = 0, началась программа;
2. ~30-100 строк загрузки libc: `faccessat("/etc/ld.so.preload") = -1 ENOENT`, `openat("/etc/ld.so.cache")`, `openat(".../libc.so.6")`, `read(3, "\177ELF...")`, много `mmap`/`mprotect`, `close(3)`, потом `set_tid_address`, `set_robust_list`, `rseq`, `prlimit64`, `getrandom`;
3. **работа программы**, то, что нас интересует;
4. `exit_group(N)` и `+++ exited with N +++` (многие утилиты перед этим делают `close(0)`, `close(1)`, `close(2)`).

Шаг 2 почти одинаков у всех программ, его можно пропускать. Признаки шума: пути `/lib/...`, `ld.so`, `locale`, `mmap`/`mprotect` подряд.

### 11.2а. Если спросят про вызовы подготовки

Разбирать их не нужно, но на вопрос "а это что?" стоит уметь ответить одной фразой.

Общий ответ: "Это не bash и не моя программа, это стандартная подготовка после `execve`: в процесс загружается библиотека libc (в ней `printf`, `malloc` и обёртки системных вызовов). Она одинаковая у `cat`, `wc`, `rm` и у `parent`/`child` из ЛР2".

Если спросят про конкретный вызов:

| Вызов | Простыми словами |
|---|---|
| `openat`/`read`/`close` на `ld.so.cache`, `libc.so.6` | найти файл библиотеки libc и прочитать его заголовок |
| `mmap` | попросить у ядра кусок памяти или положить в память кусок файла (так libc попадает в процесс) |
| `munmap` | вернуть кусок памяти ядру |
| `mprotect` | поменять права на кусок памяти, например сделать "только чтение", чтобы код и таблицы нельзя было случайно испортить |
| `brk` | увеличить кучу, из которой `malloc` раздаёт память |
| `set_tid_address`, `set_robust_list`, `rseq` | служебная настройка libc для потоков; делается при запуске любой программы, даже если поток один |
| `prlimit64` | узнать лимит, здесь максимальный размер стека |
| `getrandom` | получить 8 случайных байт; `malloc` делает из них ключ для защиты кучи от ошибок вроде двойного `free` |
| `faccessat("/etc/ld.so.preload") = -1 ENOENT` | проверка необязательного файла настроек загрузки, его нет, это нормально |

### 11.3. Как найти "своё"

- **grep по тому, что знаешь**: имя файла, текст, который программа печатает.
  `grep -n 'out.txt' bash.log`, `grep -n 'hello' bash.log`, `grep -n 'execve\|clone\|wait4' bash.log`.
- **Следи за номерками.** Увидел `openat(...) = 3`, дальше ищи `3`: где его читают, куда `dup`, когда `close`. С `-y` проще: видно `3</work/lab1/out.txt>`.
- **Следи за PID.** После `clone(...) = 150` все строки `150 ...` это ребёнок.
- **Фильтруй сразу**: `strace -f -e trace=pipe2,clone,dup2,dup3,execve,wait4 ...` показывает только нужные вызовы.
- `<unfinished ...>` и `<... read resumed>`: при `-f` два процесса делают вызовы одновременно, strace разрезает строку одного, чтобы вставить строку другого. Склеивай мысленно по PID.
- `--- SIGCHLD {...} ---` это пришёл сигнал, `+++ exited with 0 +++` процесс завершился.

### 11.4. Ошибки, которые не ошибки

- `newfstatat("/usr/local/sbin/cat") = -1 ENOENT` и ещё несколько: bash ищет программу по каталогам `PATH` по очереди. Нормально.
- `faccessat("/etc/ld.so.preload") = -1 ENOENT`: загрузчик проверяет необязательный файл. Нормально.
- `connect(..."/var/run/nscd/socket") = -1 ENOENT`: нет демона кеша имён, libc читает `/etc/passwd`. Нормально.
- `ioctl(..., TCGETS) = -1 ENOTTY`, `lseek(0, ...) = -1 ESPIPE`: программа проверяет, терминал ли это и можно ли перематывать. Нормально.
- `close(4) = -1 EBADF` в bash: закрыл уже закрытое. Безвредно.

### 11.5. Почему имена не как в C

| В C | В трассе | Почему |
|---|---|---|
| `fork()` | `clone(...SIGCHLD...)` | glibc делает `fork` через общий вызов `clone` |
| `open(path, ...)` | `openat(AT_FDCWD, path, ...)` | `AT_FDCWD` = "относительно текущего каталога" |
| `pipe(fds)` | `pipe2(fds, 0)` | `pipe2` = `pipe` с флагами |
| `waitpid(pid, ...)` | `wait4(pid, ..., NULL)` | `wait4` = `waitpid` + статистика ресурсов |
| `dup2(a, b)` | `dup3(a, b, 0)` на arm64, `dup2` на x86-64 | в arm64 нет старого `dup2` |
| `stat`, `access` | `newfstatat`, `faccessat` на arm64 | та же причина |
| `exit(0)` | `exit_group(0)` | завершить все потоки процесса |
| `printf`, `fgets`, `getline` | `write`, `read` | stdio копит данные в буфере и зовёт `write`/`read` реже |

### 11.6. Словарик вызовов из трасс

| Группа | Вызовы |
|---|---|
| Процессы | `clone` создать, `execve` сменить программу, `wait4` ждать ребёнка, `exit_group` выйти, `getpid`/`getppid` свой PID и PID родителя, `getpgid` группа процессов |
| Файлы | `openat` открыть, `read`/`write`, `close`, `lseek` позиция, `newfstatat`/`fstat` информация о файле, `faccessat` проверка прав, `unlinkat` удалить, `getdents64` прочитать каталог |
| Дескрипторы | `dup2`/`dup3` переклеить, `fcntl` копия номера (`F_DUPFD`) и флаги (`FD_CLOEXEC`), `ioctl` команды устройству (терминалу) |
| IPC | `pipe2` труба, `socket`/`connect` сокет |
| Сигналы | `rt_sigaction` обработчик, `rt_sigprocmask` блокировка, `rt_sigreturn` выход из обработчика, `kill` послать |
| Память | `mmap`/`munmap` отобразить/убрать память (библиотеки, большие буферы), `mprotect` права на память, `brk` куча для `malloc` |
| Прочее | `getuid`/`geteuid`/`getgid`/`getegid` кто я, `getrandom` случайные байты, `uname` имя системы, `set_tid_address`/`set_robust_list`/`rseq`/`prlimit64` инициализация libc |

## 12. Shell-операторы на уровне вызовов

Всё ниже снято командой `strace -f -e trace=openat,dup2,pipe2,clone,execve,wait4,getdents64,write bash -c '...'` на x86-64 (поэтому `dup2`, а не `dup3`). Загрузка библиотек убрана.

**`>` перезаписать файл.** Открыть с `O_TRUNC` (обрезать до 0) и переклеить на 1. Для встроенной команды bash делает это у себя и потом возвращает stdout (раздел 4, трасса из `bash.log`). Для внешней программы делает `fork`, в ребёнке `open` + `dup2`, потом `exec`, возвращать ничего не надо:

```
openat(AT_FDCWD, "out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3     O_TRUNC: обрезать до 0
```

**`>>` дописать в конец:**

```
openat(AT_FDCWD, "app.txt", O_WRONLY|O_CREAT|O_APPEND, 0666) = 3    O_APPEND вместо O_TRUNC
dup2(3, 1) = 1
```

**`<` ввод из файла** (`cat < in.txt`):

```
1792 openat(AT_FDCWD, "in.txt", O_RDONLY) = 3
1792 dup2(3, 0) = 0                                  номер 0 теперь файл
1792 execve("/usr/bin/cat", ["cat"], ...) = 0        cat без аргументов читает 0
```

Это ровно то, что делает ЛР2 для ребёнка.

**`2>` stderr в файл** (`ls nope 2> err.txt`): `openat(...) = 3`, `dup2(3, 2)`.

**`2>&1` и почему порядок важен.** `2>&1` значит `dup2(1, 2)`: "сделай 2 тем же, чем сейчас является 1". Shell выполняет перенаправления слева направо.

```
ls nope > all.txt 2>&1                 ls nope 2>&1 > out2.txt
openat("all.txt") = 3                  dup2(1, 2)     2 = терминал (то, чем был 1)
dup2(3, 1)     1 = файл                openat("out2.txt") = 3
dup2(1, 2)     2 = файл                dup2(3, 1)     1 = файл
итог: оба в файл                       итог: ошибки на терминал, вывод в файл
```

**`|` конвейер**: `pipe2`, два `clone`, в одном ребёнке `dup2(запись, 1)`, в другом `dup2(чтение, 0)`, два `execve`, два `wait4`. Трасса в отчёте ЛР1, раздел 4.

**`;`** просто по очереди: bash ждёт первую команду (`wait4`) и запускает следующую.

**`&&` и `||`**: следующая команда запускается, только если код выхода предыдущей 0 (для `&&`) или не 0 (для `||`). `false && echo yes`: в трассе нет ни одного `write`. `false || echo no`: есть `write(1, "no\n", 3)`. `false` встроена в bash, поэтому даже `clone` нет.

**`&` в фоне** (`sleep 0.2 & echo bg`): bash делает `clone` и, не дожидаясь, сразу выполняет следующую команду:

```
clone(...) = 1839
1838 write(1, "bg\n", 3) = 3                          bash уже печатает, sleep ещё работает
openat(AT_FDCWD, "/dev/null", O_RDONLY) = 3           в ребёнке: stdin фоновой задачи = /dev/null
dup2(3, 0) = 0
execve("/usr/bin/sleep", ["sleep", "0.2"], ...) = 0
```

**`$(...)` подстановка вывода** (`x=$(echo hi)`): bash создаёт трубу, запускает команду в ребёнке со stdout в трубу, сам читает трубу до EOF и кладёт текст в переменную:

```
pipe2([3, 4], 0) = 0
clone(...) = 1824
1824 dup2(4, 1) = 1
1824 write(1, "hi\n", 3) = 3
```

**`*` шаблон** (`echo *.txt`): раскрывает **bash**, а не программа. bash читает каталог и подставляет имена, `echo` получает уже готовый список:

```
openat(AT_FDCWD, ".", O_RDONLY|O_NONBLOCK|O_CLOEXEC|O_DIRECTORY) = 3
getdents64(3, /* 10 entries */, 32768) = 312
write(1, "all.txt app.txt err.txt in.txt o"..., 52) = 52
```

**Кавычки.** `'...'` всё буквально, ничего не раскрывается. `"..."` раскрываются `$переменные` и `$(...)`, но не `*` и пробелы не делят на слова. Без кавычек раскрывается всё. Пример: `echo '*'` печатает звёздочку, `echo *` печатает файлы. Поэтому команда в ЛР1 в одинарных кавычках: всё внутри должен разобрать запущенный bash, а не тот, в котором ты набираешь.

## 13. Построчный разбор ЛР2

**Вариант 19 (группа 5).** Родитель создаёт двух детей. Первой строкой пользователь вводит имя файла для child1, второй строкой — для child2. Дальше вводит строки; родитель отправляет каждую с вероятностью 80% в pipe1 (к child1), иначе в pipe2 (к child2). Дети удаляют из строк гласные и пишут результат в свой stdout, который подменён файлом.

```
                        ┌──── pipe1 (80%) ───► child1: stdin = pipe1, stdout = файл 1
пользователь ──► parent ┤
                        └──── pipe2 (20%) ───► child2: stdin = pipe2, stdout = файл 2
```

Файлы: [parent.c](lab2/parent.c), [process.c](lab2/process.c) + [process.h](lab2/process.h), [child.c](lab2/child.c), [vowels.c](lab2/vowels.c) + [vowels.h](lab2/vowels.h), [Makefile](lab2/Makefile), [tests/run_tests.sh](lab2/tests/run_tests.sh).

Зачем разбивка на `.h`/`.c`: требование курса. `.h` говорит "какие функции есть" (объявления), `.c` — "как они устроены". `#ifndef PROCESS_H ... #endif` защищает от двойного подключения.

child1 и child2 — **одна и та же программа** `child`, запущенная два раза. Разными программами по заданию должны быть родитель и ребёнок, это выполнено.

### 13.1. parent.c

**Подготовка.**

```c
if (signal(SIGPIPE, SIG_IGN) == SIG_ERR) { ... }
```
Если ребёнок умрёт, а родитель напишет в его трубу, ядро пошлёт `SIGPIPE`, и родитель умрёт молча. С `SIG_IGN` `write` просто вернёт -1 с `EPIPE`, родитель напечатает ошибку и всё равно дождётся детей.

```c
if (read_filename(filename1, sizeof(filename1), "child1") != 0) return 1;
if (read_filename(filename2, sizeof(filename2), "child2") != 0) return 1;
```
`read_filename` читает строку через `fgets`, отрезает `\n` (`strcspn` находит его позицию, туда пишется `\0`) и проверяет, что имя не пустое.

```c
int file1 = open(filename1, O_WRONLY | O_CREAT | O_TRUNC, 0644);
int file2 = open(filename2, O_WRONLY | O_CREAT | O_TRUNC, 0644);
```
Файлы открываются **на запись**: `O_WRONLY` — только запись, `O_CREAT` — создать, если нет, `O_TRUNC` — очистить, если есть, `0644` — права нового файла (владелец читает и пишет, остальные только читают). Номерки 3 и 4. Если второй не открылся, первый закрывается.

```c
pipe(pipe1);   // 5 (чтение), 6 (запись)
pipe(pipe2);   // 7 (чтение), 8 (запись)
```
До `fork`, чтобы дети унаследовали концы.

```c
int all_fds[6] = {file1, file2, pipe1[0], pipe1[1], pipe2[0], pipe2[1]};
pid_t child1 = start_child(CHILD_PATH, "child1", pipe1[0], file1, all_fds, 6);
pid_t child2 = start_child(CHILD_PATH, "child2", pipe2[0], file2, all_fds, 6);
```
Аргументы `start_child` по порядку: какую программу запустить (`./child`), под каким именем (оно станет `argv[0]` ребёнка и попадёт в его логи), что подставить в stdin, что подставить в stdout, какие номерки закрыть. Читается так: "запусти child1, чтобы он читал из pipe1 и писал в файл 1, остальные 6 номерков закрой". Если не создался второй ребёнок, родитель закрывает всё (первый получит EOF и завершится) и ждёт первого.

```c
close_or_report(file1);
close_or_report(file2);
close_or_report(pipe1[0]);
close_or_report(pipe2[0]);
```
Родитель только пишет в трубы. Файлы и концы чтения нужны детям, у родителя они лишние.

```c
srand(time(NULL) ^ getpid());
```
Запустить генератор случайных чисел с разным начальным значением: текущее время, перемешанное (`^` — XOR) с PID. Без этого `rand()` выдавал бы одну и ту же последовательность при каждом запуске.

**Основной цикл.**

```c
while ((length = getline(&line, &capacity, stdin)) != -1) {
    int to_pipe1 = rand() % 100 < 80;
    int fd = to_pipe1 ? pipe1[1] : pipe2[1];
    if (write(fd, line, length) != length) { perror(...); exit_code = 1; break; }
    fprintf(stderr, "[parent PID=%d] строка %d -> %s\n", ...);
}
```
- `getline` читает строку любой длины, сам выделяет и растит буфер. Возвращает длину или -1, когда ввод кончился (Ctrl+D или конец файла).
- `rand() % 100` — случайное число от 0 до 99. Меньше 80 в 80 случаях из 100. Это и есть правило "с вероятностью 80%".
- `to_pipe1 ? pipe1[1] : pipe2[1]` — "если to_pipe1, то pipe1[1], иначе pipe2[1]".
- `write` в конец записи выбранной трубы.

**Завершение.**

```c
close_or_report(pipe1[1]);
close_or_report(pipe2[1]);
wait_child(child1);
wait_child(child2);
```
Закрытие концов записи — сигнал детям "больше ничего не будет": у их `read` больше нет писателей, и он вернёт 0. Без этих `close` дети ждали бы вечно, а родитель вечно ждал бы их в `waitpid` (проверено, раздел 16.3). `wait_child` внутри вызывает `waitpid`, поэтому зомби не остаётся.

### 13.2. process.c

```c
pid_t pid = fork();
if (pid == -1) { perror("parent: fork"); return -1; }
if (pid > 0)
    return pid;          // родитель: вернуть PID ребёнка в parent.c
```
`fork` возвращается дважды. Родитель получает PID ребёнка и сразу уходит обратно в `main`. Ребёнок получает 0 и идёт дальше.

```c
dup2(in_fd, STDIN_FILENO);     // child1: dup2(5, 0) — stdin = pipe1
dup2(out_fd, STDOUT_FILENO);   // child1: dup2(3, 1) — stdout = файл 1
```
Переклеить номерки. Коротко: **поменяли дескрипторы**.

```c
for (int i = 0; i < count; i++)
    close_or_report(fds_to_close[i]);
```
Закрыть все 6 исходных номерков: нужное уже лежит в 0 и 1. Важнее всего чужой конец записи. child2 унаследовал `pipe1[1]`, child1 унаследовал `pipe2[1]`. Если их не закрыть, каждый ребёнок держит конец записи трубы другого, и ни один не получит EOF: child1 ждёт, пока child2 закроет `pipe1[1]`, а child2 ждёт того же от child1. Это взаимоблокировка (проверено, раздел 16.3).

```c
execl(path, name, (char *)NULL);   // execl("./child", "child1", NULL)
perror("child: execl");
_exit(1);
```
**Стали child.** Второй аргумент `execl` — это `argv[0]` новой программы, так child узнаёт, что он child1. Список аргументов заканчивается `NULL`. Строка после `execl` выполняется, только если он не удался. `_exit`, а не `exit`: у ребёнка копия буферов `stdio` родителя, `exit` вывел бы их второй раз.

```c
int wait_child(pid_t pid)
{
    waitpid(pid, &status, 0);          // ждать именно этого ребёнка
    if (WIFEXITED(status)) ...         // завершился сам, код = WEXITSTATUS(status)
    if (WIFSIGNALED(status)) ...       // убит сигналом номер WTERMSIG(status)
}
```

### 13.3. child.c

```c
const char *name = argc > 0 ? argv[0] : "child";
```
Имя, которое передал `execl`: `child1` или `child2`. Нужно только для логов.

```c
while (getline(&line, &capacity, stdin) != -1) {
    line_count++;
    remove_vowels(line);
    ssize_t length = strlen(line);
    if (write(STDOUT_FILENO, line, length) != length) { perror(...); free(line); return 1; }
}
```
Читать строки из stdin, а stdin — это **своя труба**. Убрать гласные. Записать в stdout, а stdout — это **свой файл**. Сам child про трубы и файлы ничего не знает: он читает 0 и пишет в 1.

`getline` вернёт -1, когда родитель закроет конец записи и труба опустеет. После цикла `feof(stdin)` отличает нормальный конец от ошибки чтения.

```c
free(line);
return exit_code;
```
Освободить буфер `getline`. При выходе ядро закроет 0 и 1, файл сохранится.

### 13.4. vowels.c

```c
static const char *russian_vowels[] = { "а", "е", "ё", ..., "Я" };
```
Русская буква в UTF-8 занимает **2 байта** (`а` = `D0 B0`), латинская 1 байт. Поэтому русские гласные хранятся строками и сравниваются по 2 байта через `strncmp(position, гласная, 2)`.

```c
char *from = line;   // откуда читаем
char *to = line;     // куда пишем
while (*from != '\0') {
    if (strchr("aeiouAEIOU", *from) != NULL) from += 1;   // латинская гласная: пропустить 1 байт
    else if (is_russian_vowel(from))           from += 2;   // русская: пропустить 2 байта
    else { *to = *from; to++; from++; }                     // остальное скопировать
}
*to = '\0';
```
Два указателя по одной строке. `from` идёт по всем символам, `to` отстаёт на число выброшенных байт. Строка сжимается на месте, лишняя память не нужна. Пример: `Hello` → `H`, (`e` пропущен), `l`, `l`, (`o` пропущен) → `Hll`.

## 15. Вопросы с защиты

1. **Чем процесс отличается от программы?** Программа это файл на диске. Процесс это запущенная программа: PID, память, таблица дескрипторов, родитель. В ЛР2 одна программа `child` работает в двух процессах.

2. **Что такое файловый дескриптор? Почему файлы получили 3 и 4, а трубы 5–8?** Номер открытого объекта в таблице процесса. Ядро даёт наименьший свободный номер, 0, 1, 2 заняты.

3. **Что делает `dup2(a, b)`?** Делает так, что `b` указывает туда же, куда `a`. В ЛР2 `dup2(pipe1[0], 0)`: stdin child1 = труба; `dup2(file1, 1)`: stdout child1 = файл.

4. **Что возвращает `fork`?** Родителю PID ребёнка, ребёнку 0, при ошибке -1.

5. **Зачем `fork`, если потом `exec`?** `exec` заменяет программу текущего процесса, без `fork` исчез бы родитель. Между `fork` и `exec` ребёнок настраивает свои дескрипторы.

6. **Что сохраняется после `exec`?** PID, PPID, таблица дескрипторов, игнорируемые сигналы. Пропадают код, данные, стек, обработчики сигналов.

7. **Почему трубы создаются до `fork`?** Чтобы дети унаследовали концы тех же труб. Созданная после `fork` труба была бы у каждого своя.

8. **Зачем родителю закрывать `pipe1[1]` и `pipe2[1]` в конце?** Это сигнал детям, что строк больше не будет: их `read` вернёт 0, только когда закрыты все концы записи. Без этого — взаимоблокировка: дети ждут данных, родитель ждёт детей в `waitpid`.

9. **Зачем ребёнку закрывать все 6 номерков?** Нужное уже лежит в 0 и 1. Главное — чужой конец записи: если child2 держит `pipe1[1]`, а child1 держит `pipe2[1]`, ни один не получит EOF, программа зависнет.

10. **Зачем родителю закрывать концы чтения `pipe1[0]`, `pipe2[0]`?** Они ему не нужны. Кроме того, если ребёнок умрёт, а у трубы останется читатель (сам родитель), `write` не получит `EPIPE`, а заблокируется, когда труба заполнится.

11. **Как реализована вероятность 80%?** `rand() % 100` даёт число от 0 до 99, условие `< 80` выполняется в 80 случаях из 100. `srand(time(NULL) ^ getpid())` задаёт разное начальное значение при каждом запуске. Это не гарантия ровно 80%, а вероятность: на 20 строках может выйти 16/4, а может 18/2. На 1000 строк получается около 800 (тест проверяет диапазон 700–900).

12. **Почему child1 и child2 — одна программа?** Они делают одно и то же (удаляют гласные). Различаются только трубой и файлом, а их подставляет родитель через `dup2`. Имя для логов передаётся как `argv[0]` в `execl`.

13. **Как удаляются русские гласные?** В UTF-8 русская буква занимает 2 байта, поэтому сравниваются пары байт через `strncmp(.., 2)`. Латинские сравниваются по одному байту.

14. **Что такое зомби? Как его избежать?** Завершившийся процесс, код которого ещё не забрал родитель. Избежать: `waitpid` для каждого ребёнка.

15. **Что будет, если убить child1 (`kill -9`) во время работы?** Ядро закроет его концы. Следующий `write` родителя в pipe1 вернёт `EPIPE` (сигнал `SIGPIPE` игнорируется), родитель напечатает ошибку, закроет трубы, дождётся обоих детей и вернёт 1. `waitpid` для child1 покажет "убит сигналом 9".

16. **Что такое `SIGPIPE` и зачем его игнорировать?** Сигнал при записи в трубу без читателей, по умолчанию убивает процесс. Игнорируем, чтобы получить ошибку `EPIPE` и завершиться аккуратно.

17. **Что произойдёт при Ctrl+C?** Драйвер терминала пошлёт `SIGINT` всем процессам переднего плана: parent, child1 и child2. Обработчиков нет, все трое завершатся.

18. **Чем Ctrl+D отличается от Ctrl+C?** Ctrl+D — это конец ввода: `getline` у родителя вернёт -1, родитель штатно закроет трубы и дождётся детей. Ctrl+C — сигнал `SIGINT`, процессы убиваются.

19. **Почему в strace `clone`, `dup3`, `pipe2`, а не `fork`, `dup2`, `pipe`?** glibc реализует `fork` через общий вызов `clone`. На arm64 в ядре нет `dup2` и `pipe`, glibc зовёт `dup3(a, b, 0)` и `pipe2(fds, 0)`.

20. **Почему `_exit`, а не `exit` после неудачного `exec`?** Ребёнок содержит копию буферов stdio родителя, `exit` вывел бы их второй раз.

21. **Почему путь `./child`?** `execl` не ищет по `PATH`, путь считается от текущего каталога. Запускать нужно из `lab2`. Из другого каталога `execl` вернёт `ENOENT`, дети напишут ошибку и выйдут с кодом 1.

22. **Что будет, если родитель пишет быстрее, чем ребёнок читает?** Данные копятся в буфере трубы (64 КБ). Когда он заполнится, `write` родителя блокируется, пока ребёнок не прочитает.

### 16.1. Другое правило фильтрации

### 16.2. Другая обработка строк в ребёнке

Всё меняется в `child.c`, в строке `remove_vowels(line);`.

- **Инвертировать строку (варианты 20–22).** Добавить функцию и вызвать её вместо `remove_vowels`:

```c
void reverse_line(char *line)
{
    size_t length = strlen(line);
    if (length > 0 && line[length - 1] == '\n')
        length--;                       /* \n оставить в конце */
    for (size_t i = 0; i < length / 2; i++) {
        char tmp = line[i];
        line[i] = line[length - 1 - i];
        line[length - 1 - i] = tmp;
    }
}
```
(Для русского текста байты UTF-8 перевернутся и буквы испортятся: побайтовый разворот корректен только для латиницы. Об этом стоит сказать, если спросят.)

- **Удалять ещё и `y`:** дописать `y` и `Y` в строку `"aeiouAEIOU"` в `vowels.c`.

### 16.3. Убрать `close` и показать зависание

Каждый ждёт другого — **взаимоблокировка**, одна из причин вернуть работу по требованиям курса. Убить: `kill %1` или `pkill parent; pkill child`. Вернуть строку.

### 16.4. Другие вероятные просьбы

- **Писать PID ребёнка в файл рядом со строкой:** в `child.c` перед `write` строки сделать `dprintf(STDOUT_FILENO, "[%d] ", getpid());`.
- **Считать, сколько строк ушло в каждую трубу:** в `parent.c` два счётчика `int sent1 = 0, sent2 = 0;`, в цикле увеличивать нужный, после цикла `fprintf(stderr, "pipe1: %d, pipe2: %d\n", sent1, sent2);`.
- **Обработать Ctrl+C в родителе:** `signal(SIGINT, handler)`, где `handler` что-то выводит через `write(2, ...)`; объяснить, что `SIGKILL` так перехватить нельзя.
