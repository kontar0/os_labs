2. Теория с нуля

Системный вызов

Программа сама не может прочитать файл или создать процесс: это умеет только ядро ОС. Программа просит ядро, и такая просьба называется системным вызовом (read, write, open, fork…). Функции из стандартной библиотеки C (printf, fopen) внутри тоже сводятся к ним. strace показывает каждую такую просьбу, её аргументы и ответ ядра.

Процесс и PID

Процесс — это запущенная программа: её память, регистры и набор открытых файлов. У каждого процесса есть номер PID, а у его родителя — PPID.

Файловый дескриптор (fd)

Когда процесс открывает файл, ядро выдаёт ему маленькое число: дескриптор. У каждого процесса своя таблица «номер → объект ядра». По умолчанию в ней уже есть три строки:

fdИмяКонстанта в CОбычно указывает на
0stdin (ввод)STDIN_FILENOклавиатура / терминал
1stdout (вывод)STDOUT_FILENOэкран
2stderr (ошибки)STDERR_FILENOэкран

Аналогия: дескриптор — это номер гардеробного жетона. Программа не знает, что висит на крючке (файл, терминал или канал), она просто говорит «запиши в жетон 1». Подменишь вещь на крючке — программа и не заметит. На этом построена вся ЛР2.

pipe (неименованный канал)

pipe(fds) создаёт в ядре трубу с буфером (обычно 64 КБ) и выдаёт два дескриптора: fds[0] для чтения и fds[1] для записи. Что записали в [1], то читается из [0], по порядку.

  • Если буфер пуст, read ждёт (блокируется).
  • read возвращает 0 (EOF) только когда все пишущие концы закрыты во всех процессах. Отсюда главная ловушка: забыл закрыть лишний конец — программа зависнет навсегда.
  • Если читателей не осталось, а кто-то пишет, ядро шлёт писателю сигнал SIGPIPE (по умолчанию он убивает процесс). Если сигнал игнорировать, write просто вернёт ошибку EPIPE.

fork

fork() создаёт копию текущего процесса. После него код продолжает выполняться в двух процессах сразу. Различить их можно по возвращаемому значению:

  • 0 — мы в ребёнке;
  • > 0 — мы в родителе, число равно PID ребёнка;
  • -1 — ошибка, ребёнок не создан.

Ребёнок получает копию таблицы дескрипторов: те же номера указывают на те же файлы и каналы.

dup2

dup2(old, new) делает так, что дескриптор new указывает туда же, куда old (если new был открыт, он сначала закрывается). Например, dup2(file_fd, 0) значит «теперь stdin — это файл».

exec

execv(path, argv) заменяет программу внутри процесса на другую: код и память новые, а PID и открытые дескрипторы остаются. Поэтому мы сначала делаем dup2, а потом exec: новая программа child уже стартует с подменёнными stdin/stdout и ничего об этом не знает. При успехе exec не возвращается никогда.

waitpid и зомби

Когда ребёнок завершается, ядро хранит его код возврата, пока родитель его не заберёт. Завершившийся, но не «забранный» процесс называется зомби. waitpid(pid, &status, 0) ждёт ребёнка и забирает его статус, после чего зомби исчезает. Зомби после завершения программы — причина вернуть лабу на доработку (так написано в требованиях).

Связка, которую надо запомнить: pipe → fork → (в ребёнке) dup2 → close → exec → (в родителе) close → read → waitpid. Это ровно то, что делает bash, когда ты пишешь cat file | wc -l. Поэтому ЛР1 и ЛР2 связаны.

3. ЛР2: задание и общая схема

Вариант 6 (группа 2). Родитель читает с клавиатуры имя файла и открывает его на чтение. Создаёт ребёнка, у которого stdin = этот файл, а stdout = pipe1. Ребёнок построчно читает строки вида 1 2 3 и пишет их сумму (тип int) в stdout, то есть в канал. Родитель читает канал и печатает результат на экран.

Пример: в файле tests/data/basic.txt записано

1 2 3
10 20 30 40
-5 5
42

Программа выводит 6, 100, 0, 42.

Почему два исполняемых файла (build/parent и build/child)? Задание требует, чтобы родитель и ребёнок были разными программами. Поэтому после fork ребёнок делает execv("…/child").

4. ЛР2 по шагам: что происходит с дескрипторами

Это главный раздел, его стоит понять досконально. Номера fd и PID взяты из реального запуска (lab2/docs/strace.log): parent имел PID 13, child — PID 14.

5. ЛР2: разбор каждого файла

src/parent.c — родитель

Шаг 1. Игнорируем SIGPIPE. Если запустить ./parent | head -1, head закроется рано, и наша запись в stdout убила бы родителя сигналом. Тогда он не дождался бы ребёнка, и остался бы зомби. С SIG_IGN запись просто вернёт ошибку EPIPE.

struct sigaction sa;
memset(&sa, 0, sizeof(sa));
sa.sa_handler = SIG_IGN;                       // «игнорировать сигнал»
if (sigemptyset(&sa.sa_mask) < 0 || sigaction(SIGPIPE, &sa, NULL) < 0) {
    perror("parent: sigaction(SIGPIPE)");
    return EXIT_FAILURE;
}

parent.c:89–95

Шаг 2. Ищем программу child через resolve_child_path. Путь берётся из того же каталога, где лежит сам parent, поэтому программа работает, из какой бы папки её ни запускали.

Шаг 3. Читаем имя файла (read_filename): первая строка stdin, пробелы по краям обрезаются (trim), результат копируется через strdup, а буфер чтения освобождается.

Шаг 4. open + pipe + spawn. У каждого вызова есть проверка, и при ошибке закрывается всё, что уже было открыто:

int file_fd = open(filename, O_RDONLY);        // fd 3
if (file_fd < 0) { fprintf(stderr, "parent: open(%s): %s\n", filename, strerror(errno)); ... }

int pipe1[2];
if (pipe(pipe1) < 0) { perror("parent: pipe"); close(file_fd); return EXIT_FAILURE; }
                                               // pipe1[0]=4 (чтение), pipe1[1]=5 (запись)
pid_t pid = spawn_redirected(child_path, file_fd, pipe1[1], pipe1[0]);
//                            что запустить  stdin   stdout   что закрыть в ребёнке

parent.c:107–129

Шаг 5. Закрываем лишнее. Это самое важное место, его любят спрашивать:

/* Если не закрыть pipe1[1], read() в relay_pipe никогда не вернёт 0 — родитель зависнет. */
close(file_fd);   // файл нужен только ребёнку
close(pipe1[1]);  // родитель в канал не пишет

parent.c:134–137

Почему так? EOF на канале наступает, только когда закрыты все пишущие концы. Если родитель держит у себя открытый pipe1[1], ядро считает, что он ещё может что-то написать. Тогда read будет ждать вечно, даже когда ребёнок уже завершился.

Шаг 6. relay_pipe — пересылка. Читаем канал кусками до 4096 байт и пишем в свой stdout, пока read не вернёт 0:

for (;;) {
    ssize_t r = read(fd, buf, sizeof(buf));
    if (r < 0) { if (errno == EINTR) continue; perror("parent: read(pipe1)"); return -1; }
    if (r == 0) return 0;                        // EOF: ребёнок закрыл свой конец (завершился)
    if (write_all(STDOUT_FILENO, buf, (size_t)r) < 0) { perror(...); return -1; }
}

parent.c:65–83

EINTR означает, что вызов прервал сигнал. Это не ошибка, вызов просто повторяем.

Шаг 7. Закрываем pipe1[0] и ждём ребёнка (wait_child). Родитель возвращает 0, только если и пересылка, и ребёнок отработали без ошибок.

src/process.c — создание и ожидание процесса

pid_t spawn_redirected(const char *path, int in_fd, int out_fd, int close_fd)
{
    pid_t pid = fork();
    if (pid != 0)
        return pid;            // родитель (PID ребёнка) или ошибка (-1) — уходим отсюда

    // ---- дальше выполняется ТОЛЬКО ребёнок ----
    if (dup2(in_fd, STDIN_FILENO) < 0)  { perror("child: dup2(stdin)");  _exit(127); }  // 0 ← файл
    if (dup2(out_fd, STDOUT_FILENO) < 0) { perror("child: dup2(stdout)"); _exit(127); } // 1 → канал
    if (in_fd != STDIN_FILENO && close(in_fd) < 0)   perror(...);  // закрыть fd 3 (копия есть в 0)
    if (out_fd != STDOUT_FILENO && close(out_fd) < 0) perror(...); // закрыть fd 5 (копия есть в 1)
    if (close_fd >= 0 && close(close_fd) < 0)        perror(...);  // закрыть fd 4 (читающий конец)

    char *const argv[] = {(char *)path, NULL};
    execv(path, argv);         // при успехе сюда НЕ возвращаемся
    fprintf(stderr, "child: execv(%s): %s\n", path, strerror(errno));
    _exit(127);
}

process.c:12–41

  • Зачем ребёнку закрывать читающий конец fd 4? Он ему не нужен. Есть и вторая причина: если родитель закроет свой читающий конец раньше времени, писатель должен получить EPIPE. А пока у самого ребёнка открыт читающий конец, канал считается «с читателем», и EPIPE не случится.
  • Почему _exit, а не exit? exit сбросит буферы printf, унаследованные от родителя. Если в буфере что-то лежало, оно напечаталось бы дважды. _exit завершает процесс сразу, без сброса буферов.
  • Почему 127? По соглашению оболочек это код «команда не найдена / не запустилась».
int wait_child(pid_t pid)
{
    int wstatus; pid_t r;
    do { r = waitpid(pid, &wstatus, 0); } while (r < 0 && errno == EINTR);
    if (r < 0) { perror("parent: waitpid"); return -1; }
    if (WIFEXITED(wstatus))   return WEXITSTATUS(wstatus);      // завершился сам: код 0..255
    if (WIFSIGNALED(wstatus)) return 128 + WTERMSIG(wstatus);   // убит сигналом
    return -1;
}

process.c:43–66

WIFEXITED/WEXITSTATUS — макросы, которые разбирают упакованное число wstatus.

resolve_child_path читает символическую ссылку /proc/self/exe: это путь к текущему исполняемому файлу. Затем меняет имя после последнего / на child. Это работает только на Linux, на Mac /proc нет, поэтому нужен Docker.

src/child.c — ребёнок

Ребёнок не знает ни про pipe, ни про файлы. Он просто читает fd 0 и пишет в fd 1. Подмену сделал dup2 до exec.

line_reader_t lr;
lr_init(&lr, STDIN_FILENO);
while ((n = lr_next(&lr, &line)) >= 0) {           // пока есть строки
    line_no++;
    int sum; const char *bad = NULL;
    sum_status_t st = sum_line(line, &sum, &bad);
    if (st == SUM_EMPTY) continue;                   // пустая строка — пропуск
    if (st != SUM_OK) { log_msg("child", "line %ld: %s ...", ...); status = CHILD_BAD_LINES; continue; }
    char out[32];
    int len = snprintf(out, sizeof(out), "%d\n", sum);
    if (write_all(STDOUT_FILENO, out, (size_t)len) < 0) { ...; return CHILD_IO_ERROR; }  // в pipe1
}

child.c:38–71

Коды выхода: 0 — всё хорошо; 1 — были плохие строки, остальные посчитаны; 2 — ошибка ввода-вывода (например, обрыв канала). Ошибки во входных данных идут в stderr, а он не перенаправлен, поэтому сразу попадает в терминал и не смешивается с результатами.

Ребёнок тоже игнорирует SIGPIPE: если родитель перестал читать, write вернёт EPIPE, и ребёнок аккуратно выйдет с кодом 2. Иначе его бы молча убил сигнал.

src/sum.c — разбор строки и сумма

for (char *tok = strtok_r(line, " \t\v\f\r", &save); tok != NULL;
     tok = strtok_r(NULL, " \t\v\f\r", &save)) {
    char *end = NULL;
    errno = 0;
    long v = strtol(tok, &end, 10);                 // текст → число
    if (end == tok || *end != '\0')                  // "abc" или "2x" — не число
        { *bad_token = tok; return SUM_BAD_TOKEN; }
    if (errno == ERANGE || v < INT_MIN || v > INT_MAX)  // не влезает в int
        { *bad_token = tok; return SUM_RANGE; }
    if (__builtin_add_overflow(sum, (int)v, &sum))  // сумма переполнила int
        return SUM_OVERFLOW;
    count++;
}

sum.c:16–33

  • strtok_r режет строку на слова по пробелам и табам. Версия _r хранит своё состояние в save, а не в глобальной переменной.
  • strtol кладёт в end место, где остановился разбор. Если end не дошёл до конца слова, в слове был мусор.
  • Числа типа int занимают 32 бита: от −2147483648 до 2147483647. Переполнение int в C — неопределённое поведение, поэтому сумма считается через встроенную функцию gcc/clang __builtin_add_overflow: она возвращает true, если результат не поместился.

src/io_utils.c — ввод-вывод

lr_next — чтение строки произвольной длины поверх голого read. Идея такая: read отдаёт кусок до 4096 байт, и в нём может быть полстроки или несколько строк сразу.

  1. Если буфер buf пуст, делаем read. Вернул 0 — это EOF: отдаём последнюю строку без \n, если что-то накопилось, иначе возвращаем −1.
  2. Ищем \n в непрочитанной части буфера (memchr).
  3. Копируем кусок до \n (или весь остаток) в line. Если line мала, ensure_cap удваивает её через realloc.
  4. Нашли \n — строка готова. Не нашли — читаем дальше.
  5. Убираем \r в конце (файлы из Windows) и ставим \0.

Поэтому тест с 200 000 чисел в одной строке проходит: строка растёт как угодно.

write_all: write имеет право записать меньше, чем просили (частичная запись). Функция повторяет вызов, пока не допишет всё, и пропускает EINTR.

log_msg печатает в stderr строку вида [child PID=14] started, PPID=13. Требования просят показывать PID, чтобы было видно, что работают разные процессы. Сообщение пишется одним write, чтобы строки двух процессов не перемешивались.

Почему в трассе clone, dup3, pipe2, openat, wait4, а в коде fork, dup2, pipe, open, waitpid? Ответ обязательно надо знать. Функции в коде — обёртки из библиотеки glibc, а в ядро она передаёт другие, более общие вызовы. Трасса снималась на ARM (aarch64, Docker на Mac с Apple Silicon), а там у ядра вообще нет старых вызовов fork/dup2/pipe/open. Есть только clone/dup3/pipe2/openat. waitpid в glibc реализован через wait4.

Обрати внимание, что строки 13 и 14 перемешаны: процессы работают одновременно. <unfinished ...> / <... resumed> значит, что вызов начался, его прервала запись другого процесса, а потом он продолжился. Это и есть демонстрация конкурентного выполнения, которую просят в требованиях.

10. Вопросы на защите и ответы

Что возвращает fork и как отличить родителя от ребёнка?

В ребёнке 0, в родителе PID ребёнка, при ошибке −1 (например, EAGAIN — превышен лимит процессов). В spawn_redirected условие if (pid != 0) return pid; отправляет родителя (и ошибку) обратно в main, а ребёнок идёт дальше, к dup2.

Что наследует ребёнок после fork?

Копию памяти (copy-on-write: страницы реально копируются только при записи), копию таблицы дескрипторов (указывают на те же открытые файлы и общую позицию в файле), обработчики сигналов, рабочий каталог, переменные окружения. Не наследуются PID и ожидающие сигналы.

Что делает exec и что остаётся после него?

Загружает в процесс новую программу: код, данные и стек новые. Остаются PID, PPID и открытые дескрипторы (кроме помеченных O_CLOEXEC). Обработчики сигналов сбрасываются, но игнорирование (SIG_IGN) сохраняется. При успехе exec не возвращается.

Зачем dup2 и почему до exec?

dup2(file_fd, 0) делает stdin ребёнка файлом, dup2(pipe1[1], 1) делает stdout каналом. Делать это нужно до exec, потому что после exec выполняется уже код child.c, а он про файл и канал ничего не знает. Он просто читает 0 и пишет в 1. Так работают все перенаправления в shell.

Что будет, если родитель не закроет pipe1[1]? частый

Родитель зависнет навсегда. read на канале вернёт 0 (EOF), только когда закрыты все пишущие концы. Ребёнок свой закроет при завершении, но копия у родителя останется открытой, поэтому ядро будет ждать данных от самого родителя.

Как родитель узнаёт, что данные кончились?

Ребёнок завершается, ядро закрывает все его дескрипторы, в том числе пишущий конец канала (fd 1). Других писателей нет, поэтому read(pipe1[0]) у родителя возвращает 0, и цикл relay_pipe заканчивается.

Что такое зомби и как его избегаешь?

Зомби — завершившийся процесс, чей код выхода ещё не забрал родитель. От процесса осталась только запись в таблице процессов. Мы вызываем waitpid(pid, &status, 0) в wait_child, и запись удаляется. В трассе это wait4(14, …) = 14. Если бы родитель завершился, не дождавшись, ребёнка «усыновил» бы init (PID 1) и сам его забрал. Но по требованиям курса так делать нельзя.

Зачем игнорировать SIGPIPE?

Если писать в канал, у которого нет читателей, ядро посылает SIGPIPE, а по умолчанию этот сигнал убивает процесс молча. С SIG_IGN write возвращает −1 с errno = EPIPE, и программа сама решает, что делать: ребёнок пишет ошибку и выходит с кодом 2. Родитель игнорирует SIGPIPE, чтобы его не убило при ./parent | head -1 до того, как он вызовет waitpid. Проверяется тестом «broken pipe».

Что такое EINTR и почему вызов повторяют?

Блокирующий вызов (read, write, waitpid) может прервать пришедший сигнал. Тогда вызов возвращает −1 и errno = EINTR. Это не настоящая ошибка, поэтому вызов просто повторяют.

Почему в strace clone/dup3/pipe2/openat/wait4, а не fork/dup2/pipe/open/waitpid?

Функции из кода — обёртки glibc. Ядро на aarch64 не имеет старых вызовов, и glibc вызывает более общие: fork() → clone(SIGCHLD), dup2 → dup3, pipe → pipe2(…, 0), open → openat(AT_FDCWD, …), waitpid → wait4. На x86-64 часть из них видна под старыми именами.

Где у тебя обработка ошибок?

У каждого вызова: sigaction, readlink, read, open, pipe, fork, dup2, close, execv, write, waitpid, realloc, strdup. Сообщения выводятся через perror или strerror(errno). При ошибке посреди main закрывается всё, что уже было открыто (например, при ошибке pipe закрывается file_fd).

Что такое pipe внутри ядра? Какой у него размер?

Кольцевой буфер в памяти ядра, по умолчанию 64 КБ (16 страниц). Если буфер полон, write блокируется, пока читатель не освободит место. Если пуст, блокируется read. Канал однонаправленный и работает только между родственными процессами, которые унаследовали дескрипторы. Для неродственных процессов есть mkfifo (именованный канал в файловой системе).

Почему _exit(127), а не exit?

После fork у ребёнка копия stdio-буферов родителя. exit() вызвал бы их сброс и обработчики atexit, и данные могли бы напечататься дважды. _exit сразу передаёт управление ядру. 127 — общепринятый код «не удалось запустить программу».

Как защищаешься от переполнения int?

Каждое число strtol читает в long, затем проверяется диапазон [INT_MIN, INT_MAX]. Сумма считается через __builtin_add_overflow, которая сообщает о переполнении (обычное переполнение signed int в C — неопределённое поведение). Строка с переполнением пропускается с сообщением в stderr.

Что если строка длиннее 4096 байт?

lr_next склеивает её из нескольких read, а буфер line растёт удвоением через realloc. Тест «200k numbers in a line» это проверяет.

Почему stderr ребёнка не перенаправлен?

Задание требует перенаправить только stdin и stdout. stderr остаётся терминалом, поэтому диагностика (строки с PID, ошибки во входных данных) сразу видна и не смешивается с суммами в канале.
